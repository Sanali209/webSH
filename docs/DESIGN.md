# Design Document: PC Center OS (v3.0)

Этот документ описывает архитектуру **PC Center** — отказоустойчивой, модульной «Web OS» для локальной автоматизации, управления файлами и работы с LLM. Система спроектирована по принципу **Микроядра**, где ядро (Kernel) обеспечивает только базовую инфраструктуру, а вся функциональность реализуется через плагины.

> **Важно:** Архитектура ориентирована на **Доверенные Плагины (Trusted Plugins)**. Система не предоставляет песочницу для изоляции вредоносного кода. Безопасность обеспечивается на уровне проверки манифеста и репутации источника.

---

## 1. Концепция и Философия

**PC Center** — это платформа, которая превращает локальный компьютер в мощный сервер автоматизации с веб-интерфейсом.

*   **Entity-First Architecture (Ориентация на Объекты):** В ядре главной сущностью является **Объект (Entity)**, а не файл. Файл — это лишь один из типов объектов (наряду с Задачей, Заметкой, Контактом или Ссылкой).
*   **Микроядро (Micro-Kernel):** Ядро минималистично и стабильно. Оно не знает деталей реализации (как открыть файл или выполнить задачу). Его задача — управлять Реестром Объектов (Entity Registry) и делегировать операции плагинам-обработчикам (Handlers).
*   **Fail-Safe:** Падение одного плагина не должно приводить к краху всей системы.
*   **Single Source of Truth:** Все данные хранятся в едином гибридном хранилище **LanceDB**, разделенном на Центральную Таблицу Объектов и Таблицы Плагинов.
*   **Schema-Driven:** Интерфейс настроек и валидация данных строятся автоматически на основе Pydantic-схем.
*   **Core SDK:** Единый набор инструментов для разработки плагинов, скрывающий сложность PyArrow и Taskiq.

## 2. Технологический Стек

| Компонент | Технология | Роль |
| :--- | :--- | :--- |
| **Backend** | **Python 3.11+, FastAPI** | API Gateway, Orchestration, Static File Serving. |
| **Plugin System** | **Pluggy** | Механизм обнаружения и загрузки модулей. |

| **Notifications** | **Desktop-notifier** | Нативные пуш-уведомления ОС. |
| **Configs** | **SQLite** | Хранение системных настроек и реестра плагинов. |
| **Observability** | **Loguru + OpenTelemetry** | Логирование и распределенная трассировка. |

## 3. Архитектура Ядра (The Kernel)

Ядро выполняет роль операционной системы для модулей.

### 3.1. Ключевые Сервисы

1.  **Frontend Serving & API Gateway:**
    *   **Single Port (8000):** FastAPI обслуживает как API (`/api/...`), так и статические файлы фронтенда (`/`).
    *   **SPA Support:** Все запросы, не относящиеся к API, перенаправляются на `index.html`.
    *   **Plugin UI Mounting:** Статические файлы плагинов (папка `ui/`) автоматически монтируются по пути `/plugins/{id}/ui`, позволяя фронтенду динамически подгружать модули.
    *   **Error Boundaries:** Перехватывает исключения в коде плагинов, предотвращая падение сервера (500 Internal Server Error -> JSON "Plugin Unavailable").

2.  **Module Federation Loader:**
    *   Динамически импортирует Python-код плагинов.
    *   Строит **Граф Зависимостей** (Dependency Graph) для корректного порядка загрузки.

3.  **Event Orchestrator:**
    *   Шина событий (Pub/Sub) на базе `asyncio`.
    *   Поддержка **Distributed Tracing**: каждое событие имеет `correlation_id` для отслеживания цепочки вызовов.
    *   Дублирование событий в **WebSockets** для реактивного обновления UI.

4.  **Resource Controller:**
    *   Управляет воркерами **Taskiq**.
    *   **Resource Quotas:** Лимитирует количество параллельных задач для каждого плагина.

5.  **Database Orchestrator:**
    *   Управляет подключениями к **LanceDB**.
    *   Обеспечивает изоляцию данных через **Scoped Access**.
    *   Запускает миграции схем при обновлении плагинов.

6.  **Capability Registry & Entity Handlers:**
    *   Реестр возможностей плагинов.
    *   **Entity Handlers:** Плагины регистрируют обработчики для типов объектов (например, `opener:file`, `opener:task`). Ядро маршрутизирует запрос на открытие объекта (например, с фронтенда) соответствующему плагину, который знает, как обработать этот `entity_id`.

### 3.2. Жизненный Цикл Плагина (Lifecycle)

Ядро управляет состояниями через хуки:

*   `ON_LOAD`: Загрузка манифеста, проверка зависимостей, миграция схемы БД, монтирование UI ресурсов.
*   `ON_ACTIVATE`: Запуск фоновых процессов, подписка на события.
*   `ON_DEACTIVATE`: Приостановка работы, сохранение состояния.
*   `ON_UNLOAD`: Полная выгрузка, очистка ресурсов.

## 4. Слой Данных (Data Layer)

Мы используем стратегию **"Universal Entity Registry"** (Реестр Объектов) с таблицами-спутниками. Эта архитектура позволяет системе унифицированно работать с файлами, задачами, ссылками и контактами.

### 4.1. Центральная Таблица Объектов (Core Entities)
Это «телефонная книга» системы. В ней хранятся только те данные, которые нужны для идентификации и базового поиска.

| Поле | Тип | Описание |
|---|---|---|
| `entity_id` | UUID / ULID | Единственный уникальный ключ во всей системе. |
| `type` | String | Категория объекта: `file`, `task`, `contact`, `link`. |
| `created_at` | Timestamp | Время появления в системе. |
| `search_text` | String | Индексируемое поле (название, заголовок) для быстрого текстового поиска. |

### 4.2. Спутниковые Таблицы (Satellite Tables)
Вся специфика вынесена в таблицы плагинов, которые связаны с ядром через `entity_id`.

*   **Плагин Файлов (`system_fs`):** Создает таблицу, где `entity_id` привязан к `path`, `size`, `hash`, `mime_type`.
*   **Плагин Таск-трекера:** Создает таблицу, где тот же `entity_id` привязан к `status`, `priority`, `deadline`.
*   **Плагин Веб-парсера:** Привязывает `entity_id` к `url` и `domain`.

### 4.3. Связи и Граф Знаний
Объекты могут ссылаться друг на друга, создавая граф знаний.
*   Пример: Вы работаете над чертежом.
    *   Системный плагин создал объект `ID:123` типа `file`.
    *   Плагин таск-трекера создал объект `ID:999` типа `task`.
    *   Задача привязывается к файлу через поле `parent_entity_id: 123` в таблице таск-трекера.
*   Для Ядра это просто два объекта. Плагин таск-трекера реализует логику отображения связи "Задача -> Файл".

### 4.4. Преимущества Архитектуры
1.  **Глобальный поиск:** Поиск по `search_text` в ядре выдает файлы, задачи и ссылки в одном списке.
2.  **Унифицированное удаление:** Если удалить объект из ядра, все плагины получают уведомление (`entity.deleted`) и очищают свои таблицы-спутники.
3.  **Гибкость:** Добавление нового типа (например, "Контакт") не требует изменения схемы ядра — просто регистрируется новый `type`.

### 4.5. Database Access

Плагины не работают с `lancedb.connect()` напрямую. Они получают объект контекста:

```python
class PluginDatabaseContext:
    def get_my_table(self, suffix="main"):
        # Возвращает таблицу плагина
        pass

    def get_entities_table(self):
        # Возвращает Core Entities (Read/Write через SDK)
        pass
```

## 5. Точки Интеграции и Системные Плагины

Система предоставляет два уровня интеграции: **Backend (Python)** и **UI (Svelte)**, а также концепцию **Системных Плагинов**.

### 5.1. Системные Плагины (Capability Providers)

Это плагины, которые предоставляют базовые возможности. В новой архитектуре они выступают как **Entity Providers** (Поставщики Объектов).

#### Пример: `plugins/system_fs` (File System Provider)
Плагин-поставщик объектов типа `file`.
*   **Role:** Сканирует диск, создает записи в `Core Entities` (type=`file`) и заполняет свою спутниковую таблицу метаданными файлов.
*   **Capabilities:** `entity_provider:file`, `opener:file`.
*   **Frontend UI:** Файловый менеджер.

#### Пример: `plugins/system_llm` (LLM Provider)
*   **Capabilities:** `llm.embed`, `llm.generate`.
*   **Backend:** Обертка над `ollama` или `transformers` для генерации векторов.

#### Пример: `plugins/system_script_engine` (Scripting & Workflow Engine)
*   **Capabilities:** `script.run`, `workflow.node_provider`, `workflow.engine`.
*   **Features:** Выполнение графов автоматизации.

#### Пример: `plugins/system_dashboard` (Main Dashboard)
*   **Capabilities:** `ui.dashboard`.
*   **Role:** Контейнер для виджетов (Grid-сетка).

### 5.2. UI Integration Points (Svelte Slots)

Ядро предоставляет систему **Слотов** (Slots) — предопределенных мест в интерфейсе, куда плагины могут встраивать свои компоненты.

| Слот (Slot Name) | Описание |
| :--- | :--- |
| `system_tray` | Иконки в статус-баре. |
| `sidebar_nav` | Пункты в боковом меню. |
| `context_menu` | Пункты меню по ПКМ на объекте. |
| `entity_preview` | Компонент предпросмотра объекта (бывший `file_preview`). |
| `dashboard_widget` | Виджеты на главном экране. |
| `settings_panel` | Вкладка в настройках. |

## 6. Система Плагинов и Core SDK

Для упрощения разработки и унификации зависимостей вводится **Core SDK**.

### 6.1. Что дает SDK?
1.  **Entity Management:** Удобные методы для создания и поиска объектов.
2.  **Dependency Management:** Фиксированные версии библиотек.
3.  **Task Helper:** Декоратор `@sdk.background_task`.

### 6.2. Структура Плагина

```text
/plugins/my_plugin/
├── manifest.json      # Паспорт модуля
├── config.py          # Настройки
├── models.py          # Схемы таблиц-спутников
├── router.py          # API
├── backend.py         # Логика
└── ui/                # Svelte компоненты
```

### 6.3. Манифест (`manifest.json`)

```json
{
  "id": "task_tracker",
  "type": "user",
  "name": "Task Tracker",
  "version": "1.0.0",
  "capabilities": ["entity_provider:task", "opener:task"],
  "ui_extensions": [...]
}
```

### 6.4. Создание Объектов (SDK Example)

Пример того, как плагин создает задачу, привязанную к другому объекту:

```python
# Пример создания задачи, привязанной к файлу
file_entity_id = "..." # ID существующего файла из системы

# 1. Регистрация базового объекта в ядре
new_task_id = sdk.entities.create(
    type="task",
    search_text="Починить калибровку лазера"
)

# 2. Сохранение специфичных данных в таблицу плагина
sdk.db.get_table("tasks").add([{
    "entity_id": new_task_id,
    "parent_entity_id": file_entity_id,
    "priority": 1,
    "status": "todo"
}])
```

## 8. Workflow Engine & Scripting

Интеграция визуального программирования (n8n-style) и скриптинга.

### 8.1. Регистрация Узлов (Nodes)
Плагины экспортируют функциональность как "узлы" через декоратор `@workflow_node`.

```python
@workflow_node(
    id="create_task",
    name="Создать Задачу",
    inputs=[NodeInput(name="title", type="string")],
    outputs=[NodeOutput(name="task_id", type="string")]
)
async def execute_create_task(ctx, inputs):
    # Логика создания задачи через SDK
    pass
```

### 8.2. Scripting Engine Plugin
Системный плагин, отвечающий за выполнение графов и передачу данных между узлами.

## 9. Безопасность и Стабильность

1.  **Trust Model:** Доверенные плагины.
2.  **Permission Scoping:** Декларация прав в манифесте.
3.  **Isolation:** Middleware для перехвата ошибок.
4.  **Validation:** Pydantic-схемы для всех данных.
