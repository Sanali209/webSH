# Design Document: PC Center OS (v3.0 — Broker Edition)

Этот документ является финальной спецификацией архитектуры **PC Center** — модульной «Web OS», построенной на принципах ультратонкого ядра и брокерской системы сообщений.

---

## 1. Архитектурная философия

Система строится как **Брокер Возможностей (Capability Broker)**.

*   **Ядро (Kernel):** Не содержит бизнес-логики, не имеет собственной базы данных и не управляет UI. Это высокопроизводительный коммутатор сигналов.
*   **Плагины:** Самодостаточные модули (Python + JS), которые регистрируют свои «Способности» (Capabilities) и «Точки интеграции» (Slots) в ядре.
*   **Транспорт:** Единая шина на базе FastAPI, объединяющая локальные вызовы и внешние микросервисы.

---

## 2. Архитектура Ядро (The Broker)

Ядро — это FastAPI сервер, выполняющий роль диспетчера. Все взаимодействие между компонентами (включая UI) проходит через него.

### 2.1. Компоненты ядра

1.  **Switchboard (Диспетчер):** Маршрутизирует запросы между плагинами. Проверяет наличие провайдера для запрошенного домена (например, `ai.ocr`).
2.  **Registry (Реестр):** Хранит JSON-схемы (Pydantic), декларации UI-слотов и метаданные всех плагинов.
3.  **Lifecycle Hooks (**Pluggy**):** Управление жизненным циклом (например, `on_startup`, `on_plugin_load`) через систему хуков, аналогичную pytest.
4.  **Security Barrier & Auditor:** Проверяет права плагина-отправителя на вызов конкретной Capability. Блокирует неаудированные модули.
5.  **Static Server:** Раздает скомпилированный фронтенд основного Shell и динамически монтирует `/ui` папки плагинов (`app.mount`).
6.  **Startup Console (**Rich**):** Стилизованный вывод в консоль при запуске системы, отображающий статус загрузки плагинов и доступные способности.

---

## 3. Протокол обмена данными

Общение происходит через **Сигналы** (Pydantic-пакеты), передаваемые через `POST /api/v1/call`.

*   **Capability Call:** Прямой вызов функции (Request-Response).
*   **Event Emit:** Широковещательное событие (Pub/Sub) для уведомления системы (например, `file.created`).
*   **Injection:** Запрос на вставку UI-компонента в слот другого плагина.

### Формат Сигнала (CapabilityEnvelope):
```json
{
  "correlation_id": "uuid",
  "domain": "storage.vector.search",
  "params": { "query": "смета на лазер", "limit": 5 },
  "context": { "caller_id": "task_tracker", "token": "jwt_string", "parent_id": "uuid", "trace_stack": [] }
}
```

### 3.1. Сквозная трассировка (Tracing)
Каждый сигнал содержит метаданные для отслеживания цепочки вызовов:
*   `correlation_id`: ID всей бизнес-цепочки.
*   `parent_id`: ID вызывающего сигнала.
*   `trace_stack`: Список пройденных узлов с временными метками.

Системный плагин `system_logger` подписывается на шину (`*.*`) и визуализирует граф вызовов в реальном времени.

### 3.2. Реактивное состояние (Reactive Store)
Для мгновенной синхронизации без лишних API-вызовов Шелл поддерживает **Shared State Store** (`ui.state`).
*   Плагины подписываются на ключи (например, `current_project_id`).
*   **Throttling:** Все обновления состояния внутри Шелла проходят через глобальный троттлинг для предотвращения избыточных рендеров и зависаний UI.
*   При изменении значения Шелл обновляет всех подписчиков через Frontend Event Bus.

## 4. Версионность и Безопасность

### 4.1. Версионность и Адаптеры
В манифесте и запросе указывается версия контракта: `domain: "storage.write@2.0.0"`.
*   **Proxy-Adapters:** Для обеспечения совместимости Ядро может загружать легкие плагины-адаптеры, которые переводят сообщения старого формата в новый.

### 4.2. Система безопасности и Аудит
Безопасность строится на **Декларативном доступе**.

1.  **Манифест:** Плагин обязан заявить список `permissions` (например, `["network.*", "storage.read"]`).
2.  **Аудит:** При первом запуске Ядро блокирует плагин и выводит отчет пользователю с категориями риска (Low/Medium/High/Critical).
3.  **Runtime Guard:** Switchboard сверяет каждый сигнал с одобренным списком прав в SQLite-базе ядра до выполнения вызова (Schema Guard).

## 5. Базовые (Системные) Плагины

Для работы ОС необходимо наличие четырех фундаментальных модулей:

### 5.1. System Storage (The Data Hub)
*   **Capability:** `storage.metadata`, `storage.vector`, `storage.search`.
*   **Технология:** LanceDB + PyArrow.
*   **Transport Optimization:** Поддержка **Memory Mapping (mmap)** для мгновенной передачи больших векторов и таблиц без сериализации в JSON.
*   **Роль:** Хранит реестр сущностей (Entities). Другие плагины «подцепляют» свои метаданные к его глобальным ID.

### 5.2. System Executor (Task Manager)
*   **Capability:** `core.execute`.
*   **Технология:** **Taskiq** (ZeroMQ). Полная асинхронность и бесшовная интеграция с FastAPI.
*   **Роль:** Принимает тяжелые задачи, выполняет их в фоне и бросает событие `task.finished`.

### 5.3. System Shell (Desktop UI)
*   **Capability:** `ui.shell`, `ui.manager`, `ui.state`.
*   **Технология:** Svelte (Compiled Static).
*   **Центральные функции:**
    *   **5 Рабочих столов:** Переключаемые пространства.
    *   **Grid System:** Модель размещения виджетов и ярлыков на сетке.
    *   **Dashboard Logic:** Оркестрация виджетов (размер которых заявляется плагинами).
*   **Роль:** Главный графический интерфейс. Предоставляет базовые слоты (`sidebar`, `tray`, `grid`), управляет окнами и хранит **Shared State Store** для реактивной синхронизации.

### 5.4. System FS Provider
*   **Capability:** `fs.scanner`, `fs.watcher`.
*   **Технология:** **Watchdog**. Отслеживание изменений файлов в реальном времени.
*   **Роль:** Единственный плагин с прямым доступом к диску. Сканирует файлы, индексирует их в Storage и мониторит изменения.

### 5.5. System Logger (The Auditor)
*   **Capability:** `debug.trace`, `debug.log`.
*   **Технология:** **Loguru** + **OpenTelemetry**.
*   **Роль:** Сквозная трассировка сигналов. Подписывается на шину (`*.*`) и визуализирует граф вызовов и задержки (мс) в реальном времени с поддержкой `correlation_id`.

---

### 6.1. Client-side Event Bus
Для минимизации нагрузки на бэкенд, Шелл предоставляет локальную шину событий на базе `window.dispatchEvent`. 
*   **Internal Communication:** Плагин А может уведомить плагин Б об изменении UI-состояния (например, "иконка активна") без обращения к FastAPI.
*   **Reactive Updates:** Автоматическое обновление UI-компонентов при изменении ключей в Shared State Store.

---

## 7. Жизненный цикл вызова (Example Flow)

1.  Пользователь нажимает «Анализ» в контекстном меню (Slot: `file_manager.context_menu`).
2.  **Плагин OCR** отправляет сигнал через Ядро: `domain: "core.execute", params: { func: "process_ocr" }`.
3.  **Ядро** проверяет права и пересылает запрос в **System Executor**.
4.  **Executor** выполняет задачу и по готовности кидает в шину событие `ocr.done`.
5.  **Shell** ловит событие и обновляет UI.

## 8. Проектная топология

```text
/pc_center
├── main.py              # Точка входа (FastAPI + Broker initialization)
├── /core                # Switchboard, Auditor, BasePlugin SDK
├── /dist                # Скомпилированный Shell (index.html, assets/)
└── /plugins
    ├── /system_storage  # Базовый провайдер БД
    ├── /system_shell    # Основной интерфейс
    └── /user_plugin     # Модуль пользователя
        ├── manifest.json
        ├── backend.py   # Логика (на базе BasePlugin)
        └── /ui          # Статика (JS/CSS)
```

### 8.1. Управление зависимостями (The Zero-Conflict Rule)
*   **Kernel-defined Environment:** Ядро определяет единый список разрешенных библиотек (`requirements.txt`).
*   **Strict Isolation:** Плагинам запрещено приносить свои бинарные зависимости. Это гарантирует стабильность единого процесса и отсутствие конфликтов версий.
*   **Pure logic:** Использование кастомных Python-модулей разрешено только в формате pure-python внутри папки плагина.

---

## 9. Plugin SDK (The Python Framework)

Каждый плагин наследуется от `BasePlugin`, что автоматизирует его регистрацию.

```python
class TaskPlugin(BasePlugin):
    @capability("tasks.create")
    async def create(self, params: MySchema):
        # Логика выполняется здесь
        return {"id": 1}
```

---

## 10. System Inspector

Встроенный инструмент отладки (`system.inspect`):
*   **Signal Bus Tracker:** Живой лог всех сигналов.
*   **Slot Map:** Визуализация того, какие плагины заняли какие места в интерфейсе.
*   **Schema Schema:** Интерактивный список всех доступных в системе методов.

---

## 11. Итоговые Гайдлайны реализации

1.  **Strict Async:** Любая блокирующая операция > 15мс должна быть вынесена в `System Executor`.
2.  **Schema First:** Все сигналы должны иметь валидную Pydantic-схему в манифесте.
3.  **UI First:** UI плагина должен быть максимально "ленивым" и загружаться только при активации слота.

---

### Резюме
PC Center OS v3.0 — это бесконечно масштабируемая «Web OS», где Ядро неизменно оперирует только сигналами, а возможности системы определяются набором подключенных плагинов.
