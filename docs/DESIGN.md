# Design Document: PC Center OS (v4.0)

Этот документ описывает архитектуру **PC Center** — отказоустойчивой, модульной «Web OS» для локальной автоматизации, управления файлами и работы с LLM.

> **Революция Архитектуры (v4.0):** Переход на модель **"Чистого Протокола" (Clean Protocol)**. Ядро системы больше не владеет базой данных. Оно превращается в "Умный Коммутатор" (Smart Switch), управляющий только жизненным циклом плагинов и маршрутизацией сообщений.

---

## 1. Концепция и Философия

**PC Center** — это платформа, которая превращает локальный компьютер в мощный сервер автоматизации с веб-интерфейсом.

*   **Zero-DB Core (Ядро без БД):** Ядро минималистично. Оно не знает про LanceDB, SQLite или файлы. Оно оперирует только **Контрактами (Interfaces)**.
*   **Smart Switch (Умный Коммутатор):** Задача ядра — принять сигнал от одного плагина, проверить контракт (Pydantic-схему) и передать сигнал другому плагину.
*   **Protocol-First:** Все взаимодействия строятся на передаче типизированных Pydantic-объектов (Envelopes).
*   **Fail-Safe:** Падение одного плагина не должно приводить к краху всей системы.
*   **Late Binding (Позднее связывание):** Ядро не знает структуру данных плагина, пока тот не зарегистрирует свою схему.

---

## 2. Технологический Стек

| Компонент | Технология | Роль |
| :--- | :--- | :--- |
| **Backend Runtime** | **Python 3.11+, FastAPI** | API Gateway, Event Bus. |
| **Plugin System** | **Pluggy** | Механизм обнаружения и загрузки модулей. |
| **Protocols** | **Pydantic** | Описание контрактов и схем данных. |
| **Message Bus** | **AsyncIO Queue / Taskiq** | Асинхронная шина сообщений. |
| **Storage (Plugin)** | **LanceDB / SQLite** | Реализуется через системный плагин `system_storage`. |
| **Frontend** | **Svelte (Vite)** | Реактивный UI, SPA. |

---

## 3. Архитектура Ядра (The Thin Kernel)

Ядро ("Тонкое Ядро") состоит из трех ключевых компонентов:

1.  **PluginLoader:**
    *   Отвечает за поиск, валидацию манифестов и загрузку кода плагинов.
    *   Строит граф зависимостей.

2.  **SignalBus (Шина Сигналов):**
    *   Маршрутизатор Pydantic-пакетов.
    *   Реализует паттерн **Pub/Sub**.
    *   Обеспечивает **Distributed Tracing** через `correlation_id`.

3.  **LifecycleManager:**
    *   Управляет стадиями `ON_LOAD`, `ON_ACTIVATE`, `ON_UNLOAD`.
    *   Мониторит здоровье плагинов (Health Checks).

> **Внимание:** В Ядре НЕТ менеджера базы данных. Вся работа с данными делегирована плагинам.

---

## 4. Протокольная Система (The Protocol System)

Вместо жестких таблиц БД, система использует наследование Pydantic-схем.

### 4.1. Базовая модель Ядра (The Envelope)
Ядро диктует только формат "конверта".

```python
from pydantic import BaseModel
from typing import Any, Dict

class CoreSignal(BaseModel):
    """Единый формат сообщения в системе"""
    source_id: str                   # ID плагина-отправителя
    target_capability: str           # Кому (напр., "storage", "ui", "llm")
    action: str                      # Что сделать (напр., "save", "render")
    payload: Dict[str, Any]          # Данные (Pydantic-dict)
    correlation_id: str              # ID трассировки
```

### 4.2. Schema Registry (Реестр Схем)
Ядро хранит реестр Pydantic-схем, зарегистрированных плагинами.
*   Плагин A может запросить схему Плагина B для валидации данных перед отправкой.
*   Это обеспечивает **Type Safety** в динамической среде.

## 5. Слой Данных и Системные Плагины

Хранение данных теперь является ответственностью **Системного Плагина**.

### 5.1. `system_storage` (The Storage Plugin)
Этот плагин берет на себя роль "Хранилища".
*   **Владеет:** LanceDB (для векторов) и SQLite (для настроек).
*   **Capability:** `storage`.
*   **API:** Принимает сигналы с `action="save_entity"`, `action="search"`.
*   Для Ядра это просто еще один плагин. Если мы захотим сменить LanceDB на PostgreSQL, мы просто заменим этот плагин.

### 5.2. Context Passing (Передача Контекста)
Контекст "путешествует" между плагинами через цепочку ответственности (Chain of Responsibility).

**Пример: Сохранение Задачи**
1.  **User Input:** Пользователь вводит "Купить молоко".
2.  **Frontend:** Шлет сигнал в Ядро.
3.  **NLP Plugin:** Распознает намерение -> Создает объект `TaskContext` (Pydantic-модель).
4.  **Kernel:** Видит сигнал и маршрутизирует его подписчикам на `action="save_task"`.
5.  **Storage Plugin:** Получает сигнал с `TaskContext` в payload. Решает, в какую таблицу LanceDB это записать.

### 5.3. Virtual State (Виртуальное Состояние)
Ядро хранит в памяти текущий "фокус" пользователя (например, ID открытого объекта). Это позволяет плагинам подхватывать контекст (Context Awareness) без лишних запросов к диску.

## 6. Точки Интеграции и Развитие

### 6.1. Capability Discovery
Плагины объявляют свои возможности.
*   Плагин LLM говорит: "Я умею `llm.generate`".
*   Другие плагины шлют ему сигналы, не зная, использует он OpenAI или локальную Llama.

### 6.2. Преимущества Архитектуры v4.0
1.  **Backend Agnostic:** Легкая замена базы данных или движка AI.
2.  **Decoupling:** Плагины знают только о контрактах, а не о реализации друг друга.
3.  **Scalability:** Ядро остается тонким и быстрым.

### 6.3. Критика и Решения
*   **Проблема:** Потеря производительности на сериализации/десериализации Pydantic.
    *   **Решение:** Для тяжелых данных (видео, большие векторы) передавать в payload `MemoryMap` (ссылку на память), а не сами байты.
*   **Проблема:** Сложность отладки распределенной системы.
    *   **Решение:** Системный плагин-логгер (`system_logger`), который перехватывает и пишет все "конверты" в журнал событий.

## 7. UI/UX Архитектура

Фронтенд также работает по принципу событий.
*   **WebSockets:** Дублируют `CoreSignal` на клиент.
*   **Dynamic Slots:** UI плагинов рендерится на основе полученных данных и состояния системы.

---

## 8. Workflow Engine

Автоматизация строится как цепочка обработки сигналов.
*   Узлы графа — это просто функции-обработчики сигналов.
*   Scripting Engine оркестрирует поток сообщений между узлами.
