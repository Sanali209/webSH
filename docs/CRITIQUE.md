# Критика Архитектуры и Концепции PC Center (v2.0)

В этом документе проводится критический анализ предложенной архитектуры (Micro-Kernel + LanceDB Satellite + Pluggy) с целью выявить потенциальные риски, узкие места и сложности реализации.

---

## 1. Технические Риски и Узкие Места (Bottlenecks)

### 1.1. LanceDB и Множество Таблиц
**Проблема:** Стратегия "Satellite Tables" предполагает создание десятков (а потенциально сотен) таблиц в LanceDB. Хотя LanceDB быстрая, управление большим количеством мелких файлов/таблиц может привести к оверхеду файловой системы и замедлению при старте приложения (сканирование метаданных всех таблиц).
**Риск:** Фрагментация данных.
**Митигация:** Использовать механизм партицирования (Partitioning) внутри одной большой таблицы, если количество мелких таблиц превысит 100.

### 1.2. Polars и In-Memory Joins
**Проблема:** Поиск и объединение данных (RRF) происходит в оперативной памяти через Polars. Если пользователь проиндексирует 1 миллион файлов, а каждый плагин добавит вектор (1536 float32), объем данных в памяти при поиске может резко вырасти.
**Риск:** OOM (Out Of Memory) на машинах с 8GB RAM.
**Митигация:** Внедрить пагинацию на уровне ядра поиска (Streaming Search) и жесткие лимиты на количество возвращаемых строк перед Join-ом.

### 1.3. Python Global Interpreter Lock (GIL)
**Проблема:** Ядро написано на Python. Даже с асинхронностью (FastAPI), CPU-интенсивные задачи (например, вычисление хэшей или легкая обработка данных внутри ядра) могут блокировать Event Loop.
**Риск:** "Лаги" интерфейса при активной индексации.
**Митигация:** Строго выносить все CPU-задачи в отдельные процессы через Taskiq (ProcessPoolExecutor), оставляя Main Thread только для I/O.

## 2. Сложность Разработки (Complexity)

### 2.1. Высокий порог входа для создателей плагинов
**Критика:** Чтобы написать плагин, разработчик должен знать:
*   Python + Pydantic (для настроек).
*   PyArrow (для схем данных).
*   Svelte + JS Modules (для UI).
*   Концепцию Taskiq (для фоновых задач).

Это **очень сложный стек** для энтузиастов. Большинство ожидает простого "скрипта на питоне".
**Рекомендация:** Создать SDK-обертку, скрывающую PyArrow и Taskiq за простыми методами (`plugin.save(data)`, `plugin.background_task()`).

### 2.2. Сложность отладки распределенной системы
**Критика:** Ошибка может возникнуть в Svelte, уйти в API, упасть в Taskiq Worker или в базе. Без мощной системы трассировки (которую сложно настроить локально) разработчик плагина будет страдать.

## 3. Безопасность и Изоляция (Security)

### 3.1. Иллюзия изоляции в Python
**Критика:** Python не предназначен для создания "песочниц". Даже с Middleware, плагин может:
*   Вызвать `os.system("rm -rf /")`.
*   Бесконечным циклом `while True:` повесить процесс воркера.
*   Использовать `ctypes` для доступа к памяти ядра.

**Вердикт:** Это система для **доверенных** плагинов. Запускать код из интернета (как в браузере) здесь небезопасно.
**Рекомендация:** Для настоящей изоляции (если планируется Plugin Store) нужно запускать плагины в Docker-контейнерах или использовать WebAssembly (Wasm) runtime (например, Extism), но это усложнит архитектуру на порядок.

### 3.2. Dependency Hell (Ад зависимостей)
**Критика:** Плагин А хочет `numpy==1.21`, Плагин Б хочет `numpy==1.24`. В Python всё это ставится в один `site-packages`. Конфликт версий неизбежен.
**Рекомендация:** Использовать виртуальные окружения для каждого плагина (`venv`), но это усложнит загрузку модулей. Альтернатива — стандарт (Core SDK), который фиксирует версии библиотек.

## 4. UI/UX Проблемы

### 4.1. "Франкенштейн" Интерфейс
**Критика:** Если каждый плагин рендерит свои куски UI, приложение быстро потеряет визуальную целостность. Один плагин использует отступы 4px, другой — 8px.
**Рекомендация:** Жестко навязывать UI-компоненты ядра (Skeleton UI). Запретить плагинам писать свои CSS-стили, разрешить использовать только Utility-классы (Tailwind), предоставляемые ядром.

### 4.2. Динамическая загрузка Svelte
**Критика:** Компиляция Svelte компонентов "на лету" или их подгрузка без пересборки — нетривиальная задача. Vite Module Federation пока экспериментален.
**Риск:** Плагины могут ломать фронтенд при обновлении версии Svelte в ядре.

## 5. Альтернативные Архитектуры

| Архитектура | Плюсы | Минусы | Вердикт |
| :--- | :--- | :--- | :--- |
| **Monolithic (Django)** | Простота разработки, нет проблем с зависимостями. | Нет модульности, сложно расширять сообществом. | Не подходит. |
| **Microservices (Docker)** | Идеальная изоляция, любой язык плагинов. | Огромный оверхед по ресурсам (RAM/CPU) для локального ПК. | Слишком тяжело. |
| **PC Center (Micro-Kernel)** | Баланс между скоростью и модульностью. | Сложность с `Dependency Hell` и безопасностью. | **Оптимально** для Power User утилит. |

---

## Итоговое Заключение

Архитектура **PC Center** амбициозна и технически красива ("Satellite Tables" — отличное решение для гибкости данных). Однако она требует высокой дисциплины при реализации Ядра.

**Главные риски, которые нужно закрыть в первую очередь:**
1.  **Dependency Hell:** Решить, как плагины будут делить библиотеки.
2.  **SDK Complexity:** Максимально упростить API для авторов плагинов.
3.  **Memory Management:** Следить за потреблением RAM при поиске через Polars.
