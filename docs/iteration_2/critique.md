# Критика и Рекомендации: Итерация 2 (Integration & Shell)

Этот документ содержит критический анализ текущего плана Итерации 2 с целью выявления рисков и предложений по улучшению архитектуры.

---

## 1. Архитектурные Риски (Architectural Risks)

### 1.1. Single-Process Bottleneck (Узкое место единого процесса)
*   **Проблема:** Использование FastAPI как для API, так и для раздачи статики (`StaticFiles`) в одном процессе может привести к блокировкам при высокой нагрузке на ввод-вывод (I/O), особенно при одновременной загрузке тяжелых JS-бандлов плагинов.
*   **Рекомендация:** Рассмотреть использование Nginx или CDN для раздачи статики в продакшене, оставив FastAPI только как API-сервер. В рамках MVP (Итерация 2) допустимо оставить как есть, но добавить метрики времени ответа для статики.

### 1.2. Безопасность динамической загрузки (Dynamic Loading Security)
*   **Проблема:** План предполагает загрузку JS-кода плагинов через `import()`. Злонамеренный плагин может выполнить произвольный код в контексте браузера пользователя (XSS), получив доступ к `localStorage` и токенам других плагинов.
*   **Рекомендация:**
    *   Использовать `Sandboxed Iframe` для изоляции виджетов (как предложено в плане), но строго ограничить `allow` атрибуты.
    *   Внедрить Content Security Policy (CSP), запрещающую загрузку скриптов с внешних доменов.
    *   Реализовать систему разрешений (Permissions) для UI: плагин должен явно запрашивать доступ к API ядра.

### 1.3. Сложность управления состоянием (State Management Complexity)
*   **Проблема:** Синхронизация состояния между Backend (Python) и Frontend (Svelte Store) может стать нетривиальной. Если состояние столов хранится только на клиенте, оно потеряется при перезагрузке страницы.
*   **Рекомендация:**
    *   Внедрить паттерн "Backend-for-Frontend" (BFF) или использовать WebSocket для синхронизации состояния в реальном времени.
    *   Состояние рабочего стола (расположение виджетов) должно персистентно храниться в БД (LanceDB/SQLite) и загружаться при старте Шелла.

---

## 2. Проблемы Реализации (Implementation Challenges)

### 2.1. Версионирование UI-компонентов
*   **Проблема:** Если API плагина обновится (v1 -> v2), а JS-код виджета останется старым (или наоборот), возникнут ошибки runtime.
*   **Рекомендация:** Добавить поле `compatibility_version` в `manifest.json`. Ядро должно проверять, совместим ли UI плагина с текущей версией Shell SDK.

### 2.2. Отладка плагинов (Plugin Debugging)
*   **Проблема:** Разработчикам плагинов будет сложно отлаживать свои виджеты, так как они загружаются динамически внутри Шелла.
*   **Рекомендация:** Создать "Dev Mode" в Шелле, который позволяет загружать виджет с локального dev-сервера (localhost:3000), минуя сборку и переустановку плагина.

### 2.3. Валидация Манифестов
*   **Проблема:** `manifest.json` может содержать ошибки в описании UI (неверные пути, отсутствующие иконки). Это приведет к "белому экрану" или поломке Шелла.
*   **Рекомендация:**
    *   Написать жесткую JSON Schema для валидации манифеста на этапе загрузки (`core/loader.py`).
    *   При ошибке загрузки плагина Шелл должен показывать заглушку "Plugin Error", а не падать целиком.

## 3. Рекомендации по Roadmap (Roadmap Adjustments)

### Добавить в Фазу 1 (Core):
*   [ ] **Health Checks для UI**: Эндпоинт, проверяющий наличие всех заявленных в манифесте файлов (js, css, icon).
*   [ ] **CSP Middleware**: Настройка заголовков безопасности для предотвращения XSS.

### Добавить в Фазу 3 (Shell):
*   [ ] **Error Boundary**: Компонент Svelte, который ловит ошибки в виджетах и предотвращает падение всего интерфейса.
*   [ ] **Skeleton Loading**: Отображение "скелета" виджета, пока грузится его JS-бандл.

### Добавить в Фазу 5 (CI/CD):
*   [ ] **E2E Tests**: Добавить Playwright тесты, которые реально открывают Шелл, логинятся и проверяют загрузку тестового виджета.

---

## 4. Итоговая оценка (Summary)

План Итерации 2 амбициозен и технически верен для стадии MVP. Основной риск кроется в безопасности и стабильности клиентской части при подключении сторонних плагинов. Рекомендуется уделить приоритетное внимание изоляции (Iframes) и валидации (JSON Schema) на ранних этапах.
